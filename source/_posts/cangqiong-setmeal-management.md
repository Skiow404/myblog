## 背景

今天推进的是套餐管理模块，具体实现了：

- 根据 id 查询套餐（含关联菜品）
- 修改套餐（含关联菜品）
- 套餐起售 / 停售（套餐内有未起售菜品时不能起售）

这三个业务都围绕同一个事实展开：**套餐和菜品是多对多关系**，数据库层面至少涉及两张表——`setmeal`（套餐表）和 `setmeal_dish`（套餐与菜品的关联表），必要时还会 join 到 `dish` 表。

这背后体现的是数据库表的设计思想：**关系型数据要拆表存储，业务层负责把拆开的数据重新组装成前端需要的形态。**

## 一、按 id 查询套餐（含菜品）

实现顺序：

1. 根据套餐 id 查 `setmeal` 表，拿到套餐基本信息；
2. 根据套餐 id 查 `setmeal_dish` 关联表，拿到该套餐关联的所有菜品；
3. 把上面两部分数据封装到一个 VO 对象里返回。

之所以要封装成 VO，是因为返回给前端的数据既包含套餐本身，又包含"跨表组合"出来的菜品列表——这已经不是一个 Entity 能装得下的了。关于 DTO / VO / Entity 的分工，详见{% post_link backend-five-details '《技术笔记：后端开发中的五个细节》' %} 第一节。

## 二、修改套餐（含菜品关系）

修改套餐的逻辑比新增更绕，因为它同时要处理"套餐主表"和"关联表"两边：

1. 根据 id 查询套餐基本信息，`new` 一个 `Setmeal`，把前端传来的 DTO 属性拷贝进去；
2. 根据套餐 id **删除** `setmeal_dish` 里所有旧的关联记录；
3. 重新**插入**前端传来的新菜品关系数据。

第 3 步里有一个容易被忽略的点：前端传来的 DTO 里**不一定带** `setmealId`。所以在插入关联表之前，必须用 `forEach` 把套餐 id 回填到每个关联对象上：

```java
setmealDishes.forEach(item -> item.setSetmealId(id));
```

如果漏了这一步，插入的就是 `setmeal_id = NULL` 的孤儿行——数据不报错，但业务上已经脏了。这里其实还有个细节：即使前端可能已经带了 `setmealId`，后端仍要强制覆盖，以服务端为唯一真相源，防漏传、防篡改。另外，`forEach` 里的 lambda 是就地修改对象（引用语义 + 副作用），不需要接收返回值。

同样的回填逻辑在新增套餐里也有，但数据来源不同：新增时 `setmealId` 来自 `useGeneratedKeys` 回填的自增主键，修改时来自前端传的 DTO——同一个动作，来源不同，这是设计时要分清的地方。

## 三、套餐起售 / 停售

这个接口有两个判断：

1. **状态合法性判断**：纯内存判断，非法直接返回，不用碰数据库；
2. **套餐内是否有停售菜品**：这个必须查数据库，所以在 Mapper 里写一个"根据套餐 id 统计停用菜品数量"的方法作为判断条件。

两个判断的顺序和第二个判断内部判断顺序有讲究：内存判断放在前面。第二个判断内部判断逻辑借助 `&&` 的短路特性，让"停售"场景直接跳过那次关联查询。这个细节详见{% post_link backend-five-details '《技术笔记：后端开发中的五个细节》' %}第三节。

最后把前端传来的状态和 id 用 builder 包装成一个对象，调用 update 方法更新，自动填充字段（`update_time`、`update_user`）直接复用 `@AutoFill` 机制即可。

## 小结

套餐管理这三个接口，本质上是同一个设计思想的三次演练：**把"关系"从主表里拆出去，用关联表存；查询时再组装回 VO，修改时先删后插，起售停售时要跨表校验。** 只要心里有"哪些数据在主表、哪些在关联表、哪些是 join 出来的派生数据"，写起来就不会迷路。
