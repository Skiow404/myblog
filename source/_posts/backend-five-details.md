这篇记录今天在写套餐业务时顺手梳理的五个点，都是"编译通过、启动通过、接口返回正常，但功能没按预期执行"这一类问题的高发区。

## 一、DTO、VO、Entity（PO）的分工

先说最基础的三个概念，以及它们的统称 **POJO**：

| 类型 | 职责 | 典型场景 |
| --- | --- | --- |
| Entity（PO） | 对应数据库表 | 与表字段一一映射 |
| DTO | 接收用户输入 | 接口入参 |
| VO | 返回给前端展示 | 接口出参 |

但真正值得记的不是这几个词的定义，而是**为什么要拆**。举三个例子：

1. **物理隔离敏感字段**：`Employee` 实体有 `password`，但 `EmployeeLoginVO` 没有。用类型系统把密码挡在返回体之外，比"记得别返回密码"这种口头纪律可靠一万倍。
2. **承载派生数据**：`categoryName` 是 join 出来的，表里根本没这一列。它不属于任何一张表，自然需要一个单独的 VO 来装。
3. **承载跨表组合**：`List<SetmealDish>` 在 `Setmeal` 实体里放不下（一个套餐对应多条记录），所以需要 DTO / VO 来承载这种"一对多"的组合。

当然，实际项目里也有"实用主义"的破例。比如 `pageQuery` 直接返回 `Page<SetmealVO>`，`DishPageQueryDTO` 直接吃到 Mapper 层，VO 和 DTO 都下沉了。目的是让 MyBatis 就地完成 `categoryName` 的映射，省掉一次 `for` 循环手工拼接。**分层是为了清晰，破例是为了性能，两者不矛盾，但要清楚自己为什么破例。**

## 二、@AutoFill 的静默失败

`@AutoFill` 这类 AOP + 反射的自动填充，最大的坑是**静默失败**：编译通过、启动通过、接口返回正常，但 `update_time` 就是没更新。

原因通常藏在一个不起眼的判断里——AOP 切面需要拿到"完整实体"才能反射设置字段，如果传进去的是标量参数（比如只传了 `id` 和 `status`），切面拿不到实体，自然也就不填了。

由此可以总结出一条**推导出来的判断准则**（而不是死记的规则）：

- 参数是**完整实体** + 按**主键**改**单行** → 用 `@AutoFill`；
- 参数是**标量**，或者**影响多行的批量 update** → 在 SQL 里写 `now()` + `@Param` 显式传 `uid`；
- `DELETE` 语句，或者表本身就没有审计列 → 什么都不加。

这条准则的价值在于它是**推导**出来的，不是背下来的。以后遇到任何 AOP + 反射的自动填充（MyBatis-Plus 的 `MetaObjectHandler`、Spring Data 的 `@EntityListeners(AuditingEntityListener)`），都能自己判断该不该用、为什么没生效。

## 三、Java 基础的两个陷阱

### 1. Integer == Integer 是引用比较

写的 `status == StatusConstant.ENABLE` 能跑，纯粹是因为 `ENABLE = 1` 落在 `Integer` 缓存池的 `-128 ~ 127` 范围内。**改成 200 就会挂。**

正确写法是 `equals`，且常量放在前面：

```java
StatusConstant.ENABLE.equals(status)
```

一个细节同时解决两个问题：避免 NPE（`status` 为 `null` 时不会抛异常），以及做的是值比较而不是引用比较。

### 2. && 是从左往右短路的，条件的排列顺序有性能含义

我最初写的判断是：

```java
countStopById(id) > 0 && ENABLE.equals(status)
```

这会让"停售"场景白白多跑一次 join 查询——因为 `countStopById` 在前面，不管当前是起售还是停售都会先执行。

把顺序调过来：

```java
ENABLE.equals(status) && countStopById(id) > 0
```

这样"停售"时第一个条件就是 `false`，短路直接跳过数据库查询。这不是逻辑问题，是执行顺序问题——代码看起来对，性能白白浪费。

## 四、关系表外键回填的必要性

修改套餐时，把菜品关系写入 `setmeal_dish` 之前，必须回填套餐 id：

```java
setmealDishes.forEach(item -> item.setSetmealId(id));
```

搞清这件事是因为：**前端传来的 DTO 可能不包含套餐 id。** 不回填，插入的就是 `setmeal_id = NULL` 的孤儿行，数据不报错，但业务上已经脏了。

这里还有两个引申：

- **数据来源不同**：save 时套餐 id 来自 `useGeneratedKeys` 回填的自增主键；update 时来自前端传的 DTO。同一个"回填"动作，来源不同，要分清。
- **即使前端带了，也要强制覆盖**：以服务端为唯一真相源，防漏传、防篡改。

另外，`forEach` 里的 lambda 是就地修改对象（引用语义 + 副作用），不需要接返回值——这也是为什么可以直接写 `forEach` 而不用 `map`。

## 五、校验该不该加：不是道德问题，是成本问题

我最初的状态是"老师没写我就不写"。后来给套餐加了存在性校验，理由是：不加校验时，id 不存在会走 update 影响 0 行、接口仍然返回成功，前端弹出"起售成功"，但数据库里什么都没变。这种静默的假成功，比写一行脏数据更难被发现。

判断框架可以概括为：**爆炸半径 × 可逆性 × 入口多样性**

- **爆炸半径**：错了之后影响多少数据？
- **可逆性**：错了之后能不能回滚？
- **入口多样性**：这个接口会被多少个地方调用？

但更重要的是：**这套权衡的结论可以因为一个新论据而翻转。** 在这里，其实完全可以不写校验——本文想说明的不是"校验一定要加"，而是"校验是否添加"的判断标准，在具体业务场景下是可以被其他因素推翻的。比如在这个场景里，我用"脏数据"和"静默假成功"作为取舍项，最终选择加上。

结论不重要，能说清楚"为什么加 / 为什么不加"才重要。
