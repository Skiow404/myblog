## 一、Result 泛型的使用

外卖项目里的零碎知识点之一：返回结果 `Result` 的泛型尽量不要“裸”着用。没有返回的 `data` 就用 `Void`。

这样类型表达更明确，也避免后续维护时对返回内容产生歧义。

## 二、Spring MVC 参数绑定

对于 Spring MVC 的参数绑定：

- `@RequestBody`：参数从 JSON Body 而来。
- `@PathVariable`：参数由 URL 里的占位符（Path）而来。
- `@RequestParam`：参数由 Query 而来。

`@RequestParam` 有两种情况。虽然都是 Query 来源，但对于一般类型和 `List`，用 `@RequestParam` 即可。如果是 DTO（数据传输对象）、POJO（普通 Java 对象），就不需要带注解，因为不写默认按 `@ModelAttribute` 处理。

```java
// 参数来源速记
// @RequestBody   -> JSON Body
// @PathVariable -> URL 占位符
// @RequestParam  -> Query；一般类型和 List 用它
// DTO / POJO     -> 不写注解，默认按 @ModelAttribute
```

## 三、菜品起售停售与套餐联动

业务逻辑上，菜品的启用禁用业务有一个联动点：禁用一个菜品，那么套餐里包含这个菜品的套餐就应该同时被禁用。

所以还要写根据菜品 id 批量停用相关套餐的逻辑。数据库里刚好有 `setmeal_dish` 关系表，也就是子表，可以用来关联。

一开始想这种特殊单一功能的方法能不能用 `setmeal` 的 `update` 替代。思考后发现，`setmeal` 的 `update` 只能根据套餐的 id 更改一个数据的启用禁用状态，无法完成按菜品 id 批量停用关联套餐。

## 四、Mapper 设计的通用与专用

总结一下 Mapper 设计的通用与专用：如果 `where` 之后不是主键、有子查询、会影响多行数据，这三个条件任一成立，就应该用一个专用的方法。

并且对于这种专用方法，无法使用我们根据 AOP 思想自定义出的切面做出的 `AutoFill` 注解。因为 AOP 底层原理是反射，而反射只能对对象调用 setter。我们要更新时间与修改人，只能手动自己设置。

这也体现了一个设计取舍：好的抽象不追求 100% 覆盖，覆盖常见场景，特殊场景特殊处理即可。

```java
// 通用 update：按主键更新单条，适合 AutoFill
// 专用 update：按菜品 id 批量停用关联套餐，影响多行，需手动设置更新时间/修改人
```

## 五、业务校验的取舍

后来关于判断菜品 id 是否存在、状态是否异常的判断，我能理解判断本身。但我不能理解一个现象：这个业务判断了，其他也可以判断的却没有判断。

思考后得出一个取舍标准：对于会影响多行数据、爆炸范围大、传输失败会造成一连串损失、不可逆程度高、入口多样性高的业务，判断是有必要的，并且要加 `@Transactional` 注解防止脏数据产生。

相反，对于只是查询或者修改单条数据的业务：

- 爆炸范围小。
- 传输错误失败只要改一下那条数据值即可，不可逆程度低。
- 入口多样性不高。

这种业务逻辑可以省去检验，交给内部管理、JWT 和静默无害来兜底：

- 内部管理：id 是从数据库捞出来的，不存在概率低。
- JWT：令牌拦截。
- 静默无害：MyBatis 的 `update` 失败数据库不会崩，应用不抛异常，用户看不见报错。

## 小结

今天项目部分的关键有两点：一是菜品禁用要联动停用包含它的套餐，因此需要专用 Mapper 方法，并且不能依赖只能对对象 setter 生效的 AutoFill；二是业务校验不是越多越好，要结合爆炸范围、不可逆程度和入口多样性做取舍，影响多行的关键业务加事务，单条且低风险的业务可以交给内部管理和静默兜底。
