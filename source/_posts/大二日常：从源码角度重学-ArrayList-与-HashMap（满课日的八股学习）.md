## 一、 List 家族：ArrayList 与 LinkedList 的取舍

在业务开发中，我们经常需要遍历和存储数据。`ArrayList` 和 `LinkedList` 是最常用的两个实现类，它们的区别主要体现在以下几个维度：

1. **线程安全**：两者均**非线程安全**。如果要在多线程环境下使用，可以使用 `Collections.synchronizedList()` 包装，或者使用并发包下的 `CopyOnWriteArrayList`。
2. **底层数据结构**：`ArrayList` 底层是基于**动态数组**；`LinkedList` 底层是基于**双向链表**。
3. **增删效率**：
   - `ArrayList` 在末尾追加元素的时间复杂度是 O(1)，但在中间插入或删除元素时，需要移动后续元素，时间复杂度为 O(n)。
   - `LinkedList` 在头尾增删极快（O(1)），但如果要在指定位置插入或删除，需要先遍历找到该位置（O(n)）。
4. **随机访问**：`ArrayList` 实现了 `RandomAccess` 接口，支持 O(1) 的快速随机访问；而 `LinkedList` 必须从头或尾开始遍历，复杂度为 O(n)。
5. **内存占用**：`ArrayList` 会预留一定的容量空间（尾部有空闲），可能会浪费内存；`LinkedList` 除了存储数据，每个节点还要额外存储前后两个指针，内存开销更大。

**总结**：日常业务开发中，**查询多、增删少**的场景首选 `ArrayList`。（其实在项目中一般是不会使用到 LinkedList 的，需要用到 LinkedList 的场景几乎都可以使用 ArrayList 来代替，并且，性能通常会更好）

## 二、 ArrayList 的扩容机制（源码剖析）

面试常问：`ArrayList` 是怎么扩容的？
其实，`new ArrayList()` 初始化时，底层是一个**空数组（懒加载机制）**。只有当我们第一次调用 `add()` 方法时，才会进行初始化。

1. **默认容量**：首次添加元素时，默认扩容为 **10**。
2. **扩容倍数**：当数组容量满时，会触发扩容。扩容后的新容量是**原容量的 1.5 倍**。
3. **底层操作**：扩容本质是调用 `Arrays.copyOf()` 方法，在内存中开辟一块新空间，并将老数组的数据拷贝过去，这是一个非常耗费性能的操作。因此，如果在明确知道数据量的情况下，推荐在初始化时指定容量。

## 三、 HashMap 底层核心机制

`HashMap` 是面试的重灾区，今天重点梳理了它的数据结构演变、寻址过程和扩容逻辑。

### 1. 数据结构演进
- **JDK 1.8 之前**：底层是**数组 + 链表**。
- **JDK 1.8 及以后**：底层变为**数组 + 链表 + 红黑树**。引入红黑树的目的是为了解决哈希冲突严重时，链表过长导致的查询效率下降问题（链表查询 O(n)，红黑树查询 O(log n)）。

### 2. 哈希寻址与位运算
`HashMap` 是如何确定元素存放在数组的哪个位置的？
- 首先，通过 `key` 的 `hashCode()` 获取哈希值，但这还不够，还需要经过**扰动函数**（将哈希值的高 16 位与低 16 位进行异或运算），目的是让高位也参与运算，降低哈希冲突的概率。

JDK 1.8 的 hash 方法源码（相比 1.7 更加精简，原理不变）：
```java
static final int hash(Object key) {
    int h;
    // key.hashCode(): 返回散列值也就是 hashcode
    // ^: 按位异或
    // >>>: 无符号右移，忽略符号位，空位都以 0 补齐
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

对比一下 JDK 1.7 的 HashMap 的 hash 方法源码：
```java
static int hash(int h) {
    // This function ensures that hashCodes that differ only by
    // constant multiples at each bit position have a bounded
    // number of collisions (approximately 8 at default load factor).
    h ^= (h >>> 20) ^ (h >>> 12);
    return h ^ (h >>> 7) ^ (h >>> 4);
}
```

- 然后，通过 **`(n - 1) & hash`** 计算数组下标（n 为数组长度，`&` 为按位与运算）。位运算（`&`）的效率远高于取余运算（`%`）。
- 存入时，如果当前位置已有元素，会比对两者的 `hash` 和 `key`，相同则覆盖，不同则以链表形式追加（拉链法）。

*(注：基础位运算补充：`|` 按位或，只要有一个为 1 即为 1；`^` 按位异或，相同为 0 不同为 1；`~` 按位非；`<<` 左移相当于乘 2 的 n 次方；`>>` 带符号右移，`>>>` 无符号右移。)*

### 3. 链表转红黑树的条件
当发生哈希冲突时，元素会挂在链表上。但转为红黑树并不是“一到 8 就转”：
- 当链表长度达到**阈值（默认为 8）**时，会先检查当前数组的长度。如果数组长度小于 **64**，会优先选择**扩容数组**，而不是转为红黑树。
- 只有当链表长度 >= 8 且数组长度 >= 64 时，才会真正将链表转换为红黑树。

**为什么优先扩容而不是转红黑树？**
数组扩容能重新打散元素，减少哈希冲突，这在多数情况下比维护红黑树更高效。因为红黑树在插入和删除时需要保持自平衡，维护成本较高。过早引入红黑树反而会增加系统的复杂度。

### 4. 为什么 HashMap 的容量必须是 2 的幂次方？
大体可以从以下三个方面解释：
1. **位运算效率更高**：对于非负的 hash，当长度为 2 的幂次方时，`hash % length` 等价于 `hash & (length - 1)`。位运算的效率远高于取模运算，这也是 HashMap 性能高的原因之一。
2. **保证哈希值的均匀分布**：因为 `n - 1` 的二进制全是 1（例如 16-1 = 15，二进制为 1111），进行按位与运算时，结果完全取决于 hash 值的低位。这保证了在扩容之后，旧数组元素能够比较均匀地被重新分配到新数组中。
3. **扩容机制变得简单和高效**：正因为容量是 2 的幂次方，扩容后元素的新位置要么是**原索引位置**（哈希值高位为 0），要么是**原索引位置 + 原容量**（哈希值高位为 1）。不需要像 JDK 1.7 那样重新计算 hash，大大提升了扩容效率。

对于以上解释点，我们给出一个例子：

假设我们有两个不同的元素，哈希值分别为 `10101100` 和 `10100100`。

**第一步：在长度为 8 的旧数组中**
通过 `hash & (length - 1)` 计算它们应该存放的位置：

```text
元素 A (hash = 10101100):
hash       = 10101100
length - 1 = 00000111  (8 - 1)
& -----------------
index      = 00000100  (十进制为 4)

元素 B (hash = 10100100):
hash       = 10100100
length - 1 = 00000111  (8 - 1)
& -----------------
index      = 00000100  (十进制为 4)
```

可以看到，在旧数组中，因为长度只有 8，`length - 1` 的高位全是 0，所以它们都被分配到了索引为 **4** 的位置（发生了哈希冲突，挂在了同一个链表上）。

**第二步：扩容后，在长度为 16 的新数组中**
容量翻倍，`length - 1` 变成了 `00001111`。此时 JDK 1.8 只需要检查 hash 值的倒数第 4 位（新增的高位）：

```text
元素 A (hash = 10101100):
hash       = 10101100
length - 1 = 00001111  (16 - 1)
& -----------------
index      = 00001100  (十进制为 12)

元素 B (hash = 10100100):
hash       = 10100100
length - 1 = 00001111  (16 - 1)
& -----------------
index      = 00000100  (十进制为 4)
```

**原理解释：**
对比两次运算，我们发现：

1. **如果新增高位为 0**（如元素 B）：与运算结果不变，位置依然是 **4**（原索引位置）。
2. **如果新增高位为 1**（如元素 A）：与运算结果变成了 12，刚好是 **4 + 8**（原索引位置 + 原容量）。

这就是为什么 JDK 1.8 扩容极其高效的原因：不需要重新计算 hash，只需看那一位是 0 还是 1，就能决定元素是留在原地，还是移动到“原位置+原容量”的新位置。
